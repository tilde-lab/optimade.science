## Context

The app's provider list is a build-time artifact: `optimade/dist/prefetched.json` is generated by `optimade-client/prefetch.js` from the upstream `https://providers.optimade.org/providers.json` registry and imported statically in `src/services/optimade.ts:4`. At runtime the `providers` asyncable store (`src/stores/providers.ts`) exposes `Object.values(optimade.providers)` to the UI; `Providers.svelte` renders one avatar tile per entry. Selection is id-based, persisted two ways: the URL `?providers=<ids>` (single comma-separated param via `prefs.array.format='separator'`) and a localStorage mirror at `optimade-providers` (`src/config.ts:8`). There is no path today to add a provider that isn't in `prefetched.json`.

The `optimade` library already exposes `Optimade.addProvider(provider)` (`optimade-client/src/index.ts:19`), which fetches the provider's `/info`, populates `optimade.apis[id]`, probes a structures query to fill `query_limits`/`api_version`, and stores `optimade.providers[id] = provider`. The app has a precedent for a user-local + builtin merged, localStorage-persisted asyncable: the `modules` store (`src/stores/modules.ts`). Modal UX follows a local-`open` boolean pattern (`src/views/Header.svelte`) wrapping `src/layouts/Modal.svelte`.

## Goals / Non-Goals

**Goals:**
- Let a user add a runtime provider by entering only a base URL; everything else defaulted.
- The custom provider appears as a selectable avatar tile alongside builtins, with id and display name `custom`.
- Custom provider definition persists across reloads (localStorage).
- Selection of the custom provider flows through the existing URL param (`?providers=custom`) and existing selection-persistence (`optimade-providers` localStorage) without bespoke selection logic.
- Reuse `Optimade.addProvider()` for `/info` probing and enrichment — no new fetch logic in the app.

**Non-Goals:**
- Supporting multiple simultaneous custom providers (single `custom` id; re-adding overwrites). A future change can generalize.
- Editing or deleting a custom provider via UI (a re-add overwrites the same id; full CRUD is out of scope).
- Custom logos / display names per user provider. The tile falls back to the existing `OPT.png` logo and initials avatar, same as any unknown builtin id.
- Deep-linking the custom provider *definition* via URL (only its *selection* is URL-encoded; the definition lives in localStorage). Sharing a `?providers=custom` link with a peer who hasn't added the provider is explicitly out of scope.
- Modifying the `optimade-client` library, `prefetched.json`, or the prefetch script.

## Decisions

### Decision 1: Single fixed id `custom` (not user-chosen, not multi)

**Rationale**: The proposal specifies the name `custom` and that it be reflected in URL params and persistence. A single fixed id keeps the URL contract stable (`?providers=custom`), requires no UI for naming, and matches the proposal's "only URL is needed" constraint. `Optimade.addProvider` already keys `optimade.providers[id]` by id, so re-adding overwrites cleanly.

**Alternatives considered**:
- *Multiple custom providers with generated ids* (e.g. `custom-1`, `custom-2`). Rejected:超出 proposal scope; complicates URL semantics and the avatar grid; not requested.
- *User-supplied id*. Rejected: violates "only URL is needed" and risks id collisions with builtins.

### Decision 2: Separate `custom-providers` store, merged into `providers` asyncable

**Rationale**: Mirrors the proven `modules.ts` pattern — a localStorage-backed asyncable that is combined with the builtin source inside the existing `providers` asyncable's resolver. This keeps `providersSync` and all downstream consumers (`Providers.svelte`, `search.ts`) working unchanged because they simply iterate the merged array.

**Alternatives considered**:
- *Mutate `optimade.providers` directly and add a second localStorage key for definitions only.* Rejected: `optimade.providers` is the library's cache and is also seeded from `prefetched.json` on every load; a custom entry would survive only until the next `optimade.providers = prefetched.providers` assignment (which happens at module init in `src/services/optimade.ts:7-8`). Merging in the asyncable resolver is the stable injection point.
- *A `derived` store combining `builtinProviders` + `customProviders`.* Rejected: the existing `providers` store is an `asyncable` (not `derived`), and converting it would ripple through `providersSync` (`syncable(providers, [])`) and `selectedProviders`. Cheaper to keep one asyncable and merge inside its resolver.

### Decision 3: Persist definitions under a new `optimade-custom-providers` localStorage key

**Rationale**: Separates the user's *definition* of a custom provider (base URL, enriched attributes) from the *selection* state already kept under `optimade-providers`. Avoids overloading the existing key's schema and matches `modules.ts`'s one-key-per-concern approach (`lsModulesKey`).

**Alternatives considered**:
- *Reuse `optimade-providers` to store a richer object.* Rejected: existing code does `JSON.parse(localStorage.getItem(lsProviderKey))` expecting a string array of selected ids; changing its shape is a silent breaking change for existing users' stored state.

### Decision 4: Re-hydrate enriched attributes from localStorage; re-probe lazily on use

**Rationale**: `Optimade.addProvider` probes `/info` and a structures query, which is slow and may fail offline. On load we restore the saved `Types.Provider` (with its last-known `api_version`/`query_limits`/`apis` entry) into `optimade.providers` and `optimade.apis` synchronously so the tile renders and is selectable immediately. A re-probe is not forced on load; the stored enrichment is treated as good enough. If the user re-adds (re-opens the modal and submits), `addProvider` runs again and refreshes.

**Alternatives considered**:
- *Re-run `addProvider` on every load.* Rejected: adds a network round-trip and failure surface to startup; degrades offline/refresh UX.

### Decision 5: Modal UX uses local `open` state + `src/layouts/Modal.svelte` wrapper

**Rationale**: Identical to the `Header.svelte` "Optimade apps" modal (`src/views/Header.svelte:10-16`), which is the simplest in-repo pattern and already wraps `svelte-morphing-modal`. The "use new" tile is a `<label>`-wrapped `Avatar` (matching the existing tile shape in `Providers.svelte:6-35`) whose click sets `open = true`.

**Alternatives considered**:
- *URL-fragment-driven modal* (like `Results.svelte`). Rejected: deep-linking the add-provider modal is not a goal and would add fragment-collision risk with result modals.

### Decision 6: "use new" tile rendered as a trailing extra tile, not part of the `#each` over providers

**Rationale**: The tile is an *action affordance*, not a provider entry. Rendering it outside the `{#each items}` loop (as a sibling `<label>` after the loop) avoids polluting the providers array and keeps selection logic untouched. Its avatar uses the same `Avatar` component with `custom` prop and a fixed label `use new`.

**Alternatives considered**:
- *Inject a sentinel provider with id `__add__` into the list.* Rejected: would need filtering out of selection/search logic; leaks UI state into the data model.

## Risks / Trade-offs

- **[Single `custom` id limits users to one custom provider]** → Accepted per proposal scope. Re-adding overwrites. Documented as a non-goal; a future change can extend to multi.
- **[Shared `?providers=custom` links break for peers without the definition]** → Accepted; definitions are localStorage-local by design. The selection will simply not resolve on the peer's machine (the id won't be in their provider list), which is the existing behavior for any unknown id in `retrieveProviderSelections`.
- **[Stale enriched attributes in localStorage]** → If a custom provider's server changes its `/info`, the stored `api_version`/`query_limits` may lag until the user re-adds. Mitigation: re-add is one click + URL paste; search still uses the live base URL.
- **[`addProvider` failure during add]** → Network/CORS/errors from `Optimade.addProvider` must surface to the user. Mitigation: modal shows an error state and does not close on failure; nothing is written to localStorage on failure.
- **[CORS for custom providers]** → Custom provider servers must permit CORS (or the app's `corsProxyUrl`). Same constraint as builtin providers; not a regression. Mitigation: error message in modal guides the user.
- **[`retrieveProviderSelections` filters unknown ids]** → Existing logic (`src/stores/providers.ts:29-40`) filters URL-selected ids against the stored selection set. Because the `custom` id is persisted in the `optimade-providers` selection key when selected, and the custom *definition* is persisted separately, this resolves correctly. Implementation must verify the `custom` id survives the reconciliation when it's in the URL.
